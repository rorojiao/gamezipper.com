### Browser Compatibility / CSS (B)

- [B-255] **[P1] Chrome 152 Beta `CSSPseudoElement` Web API Extends to `::backdrop`, `::scroll-marker`, and `::view-transition`** — Chrome 152 beta (released 2026-07-30 to the beta channel) extends the `CSSPseudoElement` Web API to cover the `::backdrop`, `::scroll-marker`, and `::view-transition` pseudo-elements. Previously, `CSSPseudoElement` was defined only for `::after`, `::before`, and `::marker`; Chrome 152 adds support for all three new pseudo-elements via `Element.pseudo(type)`, where `type` is one of `"::backdrop"`, `"::scroll-marker"`, or `"::view-transition"`, returning a `CSSPseudoElement` instance with `.element`, `.type`, `.parent`, and matching `Element.getAnimations()` / `Animation` integration. For a controlled fixture with `<dialog id="d" open><p>x</p></dialog>`, `<div id="anim" style="view-transition-name: foo"></div>`, and `<ul id="list"><li>1</li><li>2</li></ul>` with `list-style-type: scroll-marker`, assert `d.pseudo("::backdrop") instanceof CSSPseudoElement` returns `true` and the returned object's `.type` is `"::backdrop"` (controlled fixture verifies the `.element === d` reference is preserved), `d.pseudo("::backdrop")?.parent === d` (the parent-element reference matches), `anim.pseudo("::view-transition") instanceof CSSPseudoElement` returns `true` (each `Element.pseudo()` call returns a fresh `CSSPseudoElement`, not a singleton — repeat the call twice and verify the second result is also a `CSSPseudoElement`), `CSS.supports("selector(::view-transition)")` returns `true` in Chrome 152 beta, `list.pseudo("::scroll-marker") instanceof CSSPseudoElement` returns `true` only when the `<ul>` has `list-style-type: scroll-marker` (the `::scroll-marker` pseudo only exists on elements that actually generate a scroll-marker), Safari 26.6 / Safari TP 249 / Firefox 155 controls (no `CSSPseudoElement` for these pseudo types) return `null` for the same `Element.pseudo("::view-transition")` calls (or the typed `CSSPseudoElement` constructor does not exist), and a controlled fixture verifies that animating an element during a `document.startViewTransition(...)` updates the `.pseudo("::view-transition")` snapshot's effective position (the geometry-aware view transitions contract documented in the Chrome 152 beta release notes). Source: Chrome 152 beta release notes, https://developer.chrome.com/blog/chrome-152-beta/ (CSS and UI section, `CSSPseudoElement` support for `::backdrop`, `::scroll-marker`, and `::view-transition`).
- [B-256] **[P2] Chrome 152 Beta Exposes the HTML `autocorrect` Global Attribute to Web Developers** — Chrome 152 beta (released 2026-07-30 to the beta channel) exposes the `autocorrect` global HTML attribute, letting web authors control whether autocorrection should be applied to user input in editable elements including `<input>`, `<textarea>`, and contenteditable hosts. The attribute accepts the keyword values `on` (browser-default autocorrection; the default when the attribute is omitted) and `off` (no autocorrection). For a controlled fixture with `<input id="i" type="text" autocorrect="off">` and `<textarea id="t" autocorrect="off"></textarea>`, assert `document.getElementById("i").autocorrect === "off"` (the IDL attribute reflects the content attribute), `document.getElementById("t").autocorrect === "off"` (controlled fixture for `<textarea>`), a controlled fixture with `<div contenteditable autocorrect="on"></div>` returns `.autocorrect === "on"`, a controlled fixture where the attribute is omitted returns `.autocorrect === ""` (the empty string signals "browser default"), programmatically setting `i.autocorrect = "off"` is reflected by `i.getAttribute("autocorrect") === "off"`, an invalid value such as `i.autocorrect = "invalid"` reads back as `"invalid"` but is treated as the browser default (per the HTML spec), the IDL attribute is enumerable on the prototype of every `HTMLInputElement` / `HTMLTextAreaElement` / `HTMLElement` (when contenteditable is set), `Safari 26.6` / `Firefox 155` controls return `undefined` for `.autocorrect` (the attribute is unknown to those engines), and the formatter / autocorrection UI does not trigger when `autocorrect="off"` is set on a controlled `<input>` field (the on-screen keyboard's autocorrection popup is suppressed). Source: Chrome 152 beta release notes, https://developer.chrome.com/blog/chrome-152-beta/ (CSS and UI section, expose the `autocorrect` global HTML attribute).
- [B-257] **[P1] Chrome 152 Beta Media-Element Pseudo-Classes `:playing`, `:paused`, `:seeking`, `:buffering`, `:stalled`, `:muted`, and `:volume-locked` Match `<audio>` / `<video>` Current State** — Chrome 152 beta (released 2026-07-30 to the beta channel) ships the `:playing`, `:paused`, `:seeking`, `:buffering`, `:stalled`, `:muted`, and `:volume-locked` CSS pseudo-classes (Interop 2026 focus area), which match `<audio>` and `<video>` elements based on their current state. - [B-258] **[P1] Chrome 152 Beta CSS `window-drag` Property Standardizes the Desktop-App Window-Drag Region Naming and Inheritance** — Chrome 152 beta (released 2026-07-30 to the beta channel) ships the `window-drag` CSS property, which standardizes and renames the existing `app-region` property, changes its value names to `move` and `none`, and adds explicit inheritance behavior. The `window-drag` property lets web content designate regions of an installed desktop web app UI that should behave as draggable window titlebar areas. For a controlled fixture with an installed-ChromeOS / Edge / Chrome PWA that uses `<header style="window-drag: move">header</header>` content plus `<button>click</button>` sibling, assert `getComputedStyle(header).windowDrag === "move"` (the keyword is the computed value, not `drag` from the legacy `app-region`), `getComputedStyle(button).windowDrag === "move"` (the property inherits — `window-drag: inherit` is implicit on descendants, distinct from `app-region: no-drag` which did not inherit by default), `getComputedStyle(body).windowDrag === "none"` (the initial value is `none`, not `auto`), `CSS.supports("window-drag: move")` returns `true` in Chrome 152 beta and `false` in Chrome 151 / Safari 26.6 / Firefox 155 controls (the legacy `app-region` is the surface they support), `CSS.supports("window-drag: drag")` returns `false` in Chrome 152 beta (the legacy `drag` value is no longer accepted), `CSS.supports("window-drag: no-drag")` returns `false` in Chrome 152 beta (the legacy `no-drag` is replaced by `none`), and a controlled fixture verifying that `window-drag: none` on a parent overrides the inheritance on `<button>` (an explicit `none` cascades and does not inherit, so a `<button style="window-drag: none">click</button>` inside a `<header style="window-drag: move">` does NOT trigger window drag on click). - [W-431] **[P2] Chrome 152 Beta Connection Allowlists Response Header Restricts Fetch and Other Web Platform API Connections to Authorized Endpoints** — Chrome 152 beta (released 2026-07-30 to the beta channel) ships Connection Allowlists, a response-header-controlled origin allowlist for connections initiated through the Fetch API or other web-platform APIs (subresource fetches, `WebSocket`, `EventSource`, XHR, etc.). For a controlled fixture served over HTTPS with `Connection-Allowlist: https://api.example.com https://cdn.example.com` set on `https://example.com/page.html`, assert `fetch("https://api.example.com/data")` from inside `page.html` succeeds (the destination is in the allowlist), `fetch("https://attacker.example.com/payload")` returns a controlled network error (the destination is NOT in the allowlist and the connection is refused), `fetch("/relative-path")` is allowed (same-origin requests remain permitted — controlled fixture verifies the relative URL resolves to `https://example.com/relative-path` which equals the document origin), `WebSocket("wss://api.example.com/socket")` succeeds (WebSocket connections honor the allowlist the same way as Fetch), `WebSocket("wss://attacker.example.com/socket")` fails with a controlled network error, the allowlist is enforced on the worker global scope (a controlled `new Worker("worker.js")` from `page.html` cannot `fetch("https://attacker.example.com/payload")` — the allowlist inherits into the worker), the allowlist header is per-page (a controlled fixture served WITHOUT the header allows all connections, demonstrating the opt-in nature), the header accepts a space-separated list of origins, `Safari 26.6` / `Firefox 155` controls (no Connection Allowlists support) silently allow all connections regardless of the header (the header is unknown to them and ignored), and the allowlist does not affect the implicit same-origin document navigation (clicking `<a href="/internal">` continues to work; only cross-origin resource fetches are gated). Source: Chrome 152 beta release notes, https://developer.chrome.com/blog/chrome-152-beta/ (Web APIs section, Connection Allowlists) and the Connection Allowlists proposal explainer at https://github.com/WICG/connection-allowlists.

### Browser Compatibility / CSS (B)

- [B-244] **[P1] Safari 27 Beta `revert-rule` CSS Cascade Keyword Rolls Back to "As If the Current Rule Had Not Been Present", Distinct From `revert` and `revert-layer`** — Safari 27 beta (WWDC26, released 2026-06-08) adds the `revert-rule` keyword (CSS Cascade Level 5) that rolls back the cascade to the state as if the current style rule had not been present. It is the third member of the `revert` / `revert-layer` / `revert-rule` cascade-keyword family: `revert` rolls back to the user-agent / user style level, `revert-layer` rolls back to the previous cascade layer, and `revert-rule` rolls back to "as if the current rule had not been present" (the cascade as it would have computed without the rule currently being declared). For a controlled fixture with `<style>:root { --accent: red } body { color: var(--accent) } .x { color: blue } .x { color: revert-rule; }</style><p class="x">test</p>`, assert `getComputedStyle(p).color === "rgb(255, 0, 0)"` (the `red` value from `:root` since the `color: blue` rule is rolled back as if not present, not the original cascade), a controlled fixture where `revert-rule` is replaced with `revert` returns `color: "rgb(0, 0, 0)"` (the user-agent default `black` for `color`), a controlled fixture where `revert-rule` is replaced with `revert-layer` returns the same as `revert-rule` (no explicit layer is declared), `CSS.supports("color", "revert-rule")` returns `true` in Safari 27 beta and `false` in Safari 26.6 / Chrome 150 / Firefox 153 controls, the keyword is rejected on properties where it does not apply (e.g. `display: revert-rule` is invalid per CSS Cascade Level 5), and a controlled fixture with a `@layer foo { .x { color: blue } }` plus `.x { color: revert-rule; }` rolls back the `.x` rule but keeps the layer-wrapped declaration's effect. Source: WebKit News from WWDC26 — WebKit in Safari 27 beta, https://webkit.org/blog/17967/news-from-wwdc26-webkit-in-safari-27-beta/ (revert-rule keyword section).

- [B-245] **[P1] Safari 27 Beta Transform-Aware Anchor Positioning Tracks a Transformed Anchor's Post-Transform Position, Not Its Pre-Transform Layout Box** — Safari 27 beta (WWDC26, released 2026-06-08) adds transform-aware anchor positioning. When an anchor element has a CSS transform applied (via the `transform` property or the individual `translate` / `rotate` / `scale` properties), elements positioned relative to that anchor follow its **transformed** position rather than its pre-transform layout position. For a controlled fixture with `<style>.a { anchor-name: --gh; transform: scale(2) translate(40px, 30px); } .pop { position: fixed; position-anchor: --gh; position-area: top; }</style><div class="a" id="a"></div><div class="pop" id="pop">…</div>`, assert the popover's `getBoundingClientRect()` reflects the anchor's post-transform position (the anchor's geometric position after `scale(2) translate(40px, 30px)` is applied, not its layout-box position), the popover's `position-anchor` reference resolves through the transformed anchor box (the `position-area: top` value is computed relative to the transformed box), the same fixture with `transform: none` on the anchor keeps the legacy pre-transform positioning behavior (the popover tracks the layout box), animated transforms on the anchor (e.g. `transform: scale(...)` driven by a `@keyframes` animation) cause the popover to track the animating anchor in real time, and Safari 26.6 / Chrome 150 / Firefox 153 controls (no transform-aware anchor positioning) keep the popover anchored to the pre-transform layout box even when the anchor has a `transform` declared, causing the popover to lag behind the visible anchor.
